# MODES-01 — измеренная задержка выбора героя

19 октября 2026. **PASS для исследованного desktop Chromium IAB**: длительная синхронная подготовка поз при выборе героя устранена, изображение и состояние выбора проверены до/после. Это проверка отзывчивости и первого использования анимации; полные маршруты 4.5.0 относятся к следующим gates.

## Что изменено и что измерено

Старый `MascotArtwork.GetFrame` при смене варианта готовил 192 текстуры. Новый путь создаёт запрошенную позу и затем использует кэш. Размеры карточек не уменьшены. Причина задержки подтверждена исполнением CPU-пути и браузерными замерами; причинная связь задержки именно с увеличением карточек не установлена.

| CPU-путь, .NET 10 с Unity shim | Сохранённый baseline | Lazy-подготовка |
|---|---:|---:|
| 23 смены героя: median | 331.1655 мс | 2.7650 мс |
| min / max смены | 302.3883 / 356.8039 мс | 2.3492 / 3.5273 мс |
| Повтор текущего: median | 0.0017 мс | 0.00065 мс |
| Максимум отдельного обновления состояния | 0.1454 мс | 0.1813 мс |

Источники: [CPU baseline](../Tools/CharacterLatencyProbe/report-root-baseline.json), [CPU после исправления](../Tools/CharacterLatencyProbe/report-root-lazy.json), [методика CPU](../Tools/CharacterLatencyProbe/README.md). Shim не измеряет GPU upload, браузерное событие или появление пикселей. Независимая [проверка artwork](MODES-ARTWORK.md) подтвердила все 1 536 поз, 8 previews и 2 048 выборов поз; максимум первой генерации running-позы в её отдельном CPU-прогоне — 3.347 мс.

## Реальный браузер: время до следующего paint

Основной браузерный замер — native `PerformanceEventTiming.duration`, полученный через асинхронный `PerformanceObserver`: интервал от события до следующего обновления rendering после обработки ввода. API имеет гранулярность 8 мс; это измерение браузера, не точное физическое свечение экрана телефона. Определение проверено по [W3C Event Timing, §1.5](https://www.w3.org/TR/event-timing/#sec-events-measured).

`pointerdown.startTime` сопоставлен с `sample.eventTime` с допуском ±1 мс; первоначальная отдельная desktop-проба исключена из paired baseline. [Сводка native event timing](modes-native-event-paint-summary.json):

| Выборка | Смена: count / min / median / max | Повтор текущего: count / min / median / max |
|---|---|---|
| Baseline 568×320 | 8 / 488 / **520** / 616 мс | 8 / 80 / 112 / 120 мс |
| Baseline 844×390 | 8 / 480 / **512** / 520 мс | 8 / 88 / 88 / 88 мс |
| Исправление 568×320 | 8 / 80 / **80** / 80 мс | 8 / 80 / 80 / 88 мс |
| Исправление 844×390 | 8 / 112 / **112** / 112 мс | 7 / 104 / 112 / 112 мс |

Baseline 844 получен при фактическом viewport844×390 и сохранён отдельно в [before-passive844](modes-latency-before-passive844.json). Дополнительный повтор 568 не выдаётся за desktop-проверку и не входит в эту таблицу. Последняя repeat-entry исправленного 844 ещё не пришла в observer к сохранению; её не считают нулевой или успешной. Native timing относится к следующему paint, а не к семантическому распознаванию конкретного героя; правильный выбор и изображение дополнительно подтверждены состоянием и снимками. Значения 80/112 мс не заменяются более низкими числами DOM-публикации.

## Дополнительные точки наблюдения

Использованы настоящие pointer-события, пассивная временная запись, публичная DOM-диагностика и снимки экрана. `received − eventTime` показывает вход браузерного обработчика; `stateAt − eventTime` — появление подходящего опубликованного состояния. Диагностика дискретна и не задаёт точное время изменения поля внутри Unity. `secondFrameAt` после двух rAF — дополнительный proxy; он **не является точной меткой первой физической презентации кадра**. Снимок подтверждает видимые пиксели к моменту снимка, а не первый момент их появления. Ни одна из этих величин не выдаётся за физический phone input-to-photon.

| Смена героя, пассивная выборка | Event → callback | Event → DOM state | Максимальный rAF gap возле события | Event → второй rAF, proxy |
|---|---:|---:|---:|---:|
| Baseline, 9 смен | 0.2–0.6 мс | 453.1–576.4 мс | 407.0–531.1 мс | 458.6–583.4 мс |
| Исправление 568×320, 8 смен | 0.1–0.5 мс | 40.1–59.4 мс | 31.3–32.1 мс | 81.4–114.6 мс |
| Исправление 844×390, 8 смен | 0.2–0.5 мс | 42.1–58.7 мс | 31.5–32.1 мс | 81.4–114.3 мс |

Источники: [baseline passive](modes-latency-before-passive.json), [после 568](modes-latency-after-passive568.json), [после 844](modes-latency-after-passive844.json). В каждой исправленной выборке есть также 8 повторов текущего героя: DOM state 52.4–59.1 мс при 568 и 18.3–61.3 мс при 844, без большого frame gap. [Первоначальная визуальная проверка](modes-latency-before-browser.json) дополняет пассивные замеры; задержки самой команды автоматизации не смешиваются с таблицей.

Проверены все четыре героя обеих половин и одинаковые герои. [16 настоящих быстрых кликов за 591 мс](modes-latency-rapid.json) оставили ожидаемых героев 3/3; смена своей карточки сбросила только свою готовность. При таком темпе DOM может пропустить промежуточный выбор: поздний совпавший hero ID нельзя использовать как latency конкретного быстрого клика. Поэтому этот прогон подтверждает итог и изоляцию игроков, а не новую таблицу индивидуальных задержек. [Снимок 844×390](modes-characters-844.png) проверен визуально.

## Старт и первые новые позы

[Два повторных локальных reload в той же IAB-среде](modes-startup-browser.json), с повторно используемым локальным кэшем:

| Версия | DOM ready, два прогона | Видимость подтверждена снимком |
|---|---:|---:|
| 4.4 baseline | 3832 / 3766 мс | 3938 / 3872 мс |
| 4.5 lazy | 2898 / 2874 мс | 3001 / 2972 мс |

Это не cold-network benchmark. Подготовка не перенесла прежнее полусекундное зависание в первый заезд: [новые running/air/recovery-позы](modes-lazy-first-race-frames.json) наблюдались около 11 с, 333 racing-интервала rAF, максимум 33.1 мс, ни одного >50 мс. Countdown: 93 интервала, максимум 33.2 мс; ready: максимум 33.2 мс. Во время первоначальной загрузки был один gap 131.9 мс. Эти интервалы относятся к браузерному rAF, а не к частоте DOM-диагностики и не к гарантированному FPS всех устройств.

Сохранённые данные подтверждают устранение конкретного длительного участка на проверенной машине. Физические телефоны, длительный прогон и itch.io iframe этим отчётом не проверены.
