## Семантика исправления

Состояние кольца **до события** определяет отмену награды. Столкновение по-прежнему стоит 0,5 с и замораживает движение/эффекты.

| События | Ожидаемый результат |
|---|---|
| Удар, затем контакт ещё не тронутого связанного кольца | Кольцо доступно; контакт создаёт pending, чистое окончание текущего манёвра и выход из опасной области подтверждают reward |
| Первый контакт связанного кольца точно одновременно с ударом | Collision-first учитывает pre-event state: кольцо ещё не pending, поэтому не блокируется. Контакт может создать pending в том же событии; дальнейшее подтверждение не запрещено историческим HitObstacleIds |
| Кольцо уже pending, затем удар о связанный камень | Pending отменяется, награды нет |
| Pending + hit/clear в одном интервале численного допуска | Удар имеет приоритет, награды нет; строгое совпадение исключено геометрическим зазором, подробности ниже |
| Reward уже подтверждён, затем удар | Ранее заработанный эффект остаётся; штраф отдельно |
| Удар о другой камень | Не отменяет чужую связанную награду |
| Свободное положительное / отрицательное кольцо | Немедленный контактный эффект, один раз для каждого игрока; прежнее поведение |
| Пропущенное, но не собранное кольцо | Обычный вид до ухода за край экрана; сам пропуск не создаёт failed/pending/success |

Последовательность для точного совпадения первого контакта и удара закреплена в engine и независимом harness: отмена рассматривает pending до текущего события. Подтверждённая отмена pending сохраняет отдельный визуальный статус; изменение вида касается простого пропуска.

## Риск нулевого цикла

Одного ограничения отмены только pending-кольцами недостаточно. В финальном diff также удалён прежний veto `!HitObstacleIds.Contains(zone.ObstacleId)` на подтверждении. В промежуточном варианте только с новым guard после старого удара новое pending-кольцо достигало clear с `Time=0`, но ни подтверждалось, ни отменялось. Engine воспроизвёл этот RED; отдельный процесс был остановлен через 3 с. Финальный вариант проходит большие шаги и физический финиш.

Каждое обработанное нулевое событие должно изменить состояние: untouched → pending, pending → success/failed, поверхность/эффект → следующий участок движения. Новая логика не должна повторно назначать уже выполненное подтверждение, выдавать повторное кольцо или зацикливать большой dt.

## Проверенный объём

- Сценарии hit → recovery → first collection → clear и first collection → later hit → cancellation, включая after-ring и возврат на исходную поверхность.
- Отдельные точные ties из таблицы; до/после границы события и разбиение шага ровно на контакт. Одинаковое поведение при 30/60/144 Гц и крупном dt.
- Реальное завершение шага и финиша после старого удара; штраф сохранён, bonus служит полностью и только один раз; FIFO и независимость игроков сохранены.
- Пропущенные положительные и отрицательные кольца на обеих половинах экрана: нормальный вид, пока видимы. Pending, полученная награда и отмена pending не смешиваются с пропуском.
- Физика разворота, геометрия и идеальные маршруты не меняются в этой правке.

## Повторный запуск независимых проверок

Нужен PowerShell 7. Из корня проекта в новом процессе; временные исходники размещаются вне Unity `Temp`:

```powershell
$ringAuditRoot = Join-Path $env:TEMP ('flip-rings-audit-' + [guid]::NewGuid())
New-Item -ItemType Directory -Path $ringAuditRoot | Out-Null
Copy-Item -LiteralPath Verification/v4-rings-independent-baseline.cs.txt -Destination (Join-Path $ringAuditRoot 'Baseline.cs')
Copy-Item -LiteralPath Verification/v4-rings-independent.cs.txt -Destination (Join-Path $ringAuditRoot 'RingsProbe.cs')
$coreFiles = @(Get-ChildItem -LiteralPath Assets/Scripts/Core -Filter '*.cs' | ForEach-Object FullName)
Add-Type -Path ($coreFiles + @((Join-Path $ringAuditRoot 'Baseline.cs'), (Join-Path $ringAuditRoot 'RingsProbe.cs')))
[V4Independent]::Run()
[V4RingsIndependent]::Run()
```
